# Cron 看门狗陈旧锁陷阱与补救流程

## 事故场景（2026-08-06 实测）

主任务（当日复盘 15:15）抢到互斥锁（`date +%s` 写入 `~/.hermes/cron/locks/复盘_2026-08-06.lock`），但因空闲超时/模型API hang/进程异常被杀，**未产出任何文件**。

看门狗 15:22 触发时：
- 锁检查：`LOCKED`（锁存在，timestamp=1786000537）
- 文件检查：`2026-08-06-A股复盘.md` 和 `.json` **均不存在**

## 根因

SKILL.md 中互斥锁规则写的是「看到 LOCKED -> 立即 [SILENT] 退出」。但这条规则**假设锁存在=主任务成功**，忽略了主任务抢锁后失败的情况。锁只代表「有人抢过」，不代表「有人完成了」。

## 正确行为：文件检查优先于锁检查

看门狗必须**先查文件，再查锁**。即使锁存在，也必须先检查文件是否存在：

| 锁状态 | 文件状态 | 看门狗动作 |
|--------|----------|-----------|
| 锁存在 | 文件存在(≥5KB) | [SILENT]（主任务成功） |
| 锁存在 | 文件缺失 | **执行补救**（陈旧锁） |
| 锁不存在 | 文件存在 | [SILENT]（异常但已完成） |
| 锁不存在 | 文件缺失 | 抢锁 + 执行补救 |

## 看门狗正确流程

```bash
MD=/usr/local/files/docs/stock/$(date +%Y-%m-%d)-A股复盘.md
JS=/usr/local/files/docs/stock/$(date +%Y-%m-%d)-A股复盘.json

# 第一步：先查文件（无论锁状态）
if [ -f "$MD" ] && [ -f "$JS" ] && [ $(stat -c%s "$JS" 2>/dev/null) -ge 5120 ]; then
  echo "[SILENT] 主任务已成功"
  exit 0
fi

# 第二步：文件不存在或过小 -> 需要补救（无论锁状态）
# 此时锁可能是陈旧的（主任务抢锁后失败），直接执行补救
echo "STALE_LOCK_DETECTED: 锁存在但文件缺失，执行补救"
```

## 补救执行流程

1. 确认文件确实不存在（`ls -la` 两个文件路径）
2. 按正常复盘流程采集数据（browser_navigate + browser_console 从 qt.gtimg.cn 获取指数/个股，Sina /tob/ 收评文章 + /cpbd/ 操盘必读）
3. 生成 markdown + JSON
4. API 上报（从 ~/.profile 或 config.yml 读取 API key）
5. final response **只汇报看门狗本职状态**（文件大小、API状态码、推送决策），不含股市数据

## 注意事项

- **不要清理陈旧锁**：补救时不需要删除旧锁文件或重新抢锁。锁的唯一作用是防止重复推送，文件检查才是成功判定的唯一标准。
- **看门狗 final response 纯净**：补救生成的所有股市内容只能写文件/上报API，绝不放进 final response（看门狗职责边界）。
- **单次补救**：这是唯一一次重试机会。补救失败时不创建新 cron job，如实记录失败信息。
